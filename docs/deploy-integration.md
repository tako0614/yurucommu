# Isolated Yurucommu integration peer

The product-owned entrypoint is `bun run deploy -- yurucommu-integration --environment=integration --phase=<phase>`. It is only for `https://ga-commu-20261012.yurucommu.com` and resources named `yurucommu-ga-20261012-0938-*` in the selected existing Cloudflare account. The published Worker input is the checked-in `v2.4.1` GitHub Release and its `release.lock.json` SHA-256. This does not change or repair the production `yurucommu` Worker, its credentials, data, or schema.

Phases are `preflight`, `resources`, `fresh-schema`, `recover-prefix32`, `activate`, `domain`, and the isolated `test-owner-auth` repair phase. Each invocation acts on one phase. `preflight` reads the exact zone/account and full D1, R2, KV, Queue, Worker, and filtered/paginated custom-domain inventories and refuses a name collision or denied/incomplete read. `resources` repeats that check, copies the root OpenTofu model into the private operator directory, and accepts only creation of a fresh D1 database, R2 bucket, KV namespace, two Queues, and the root module's random identifier. The root model pins D1 read replication to `disabled`, matching the observed D1 mode and preventing disabled-to-null plan drift; the exact plan and post-apply readback are still required. The Worker remains disabled. The private state and plan remain in the 0700 operator directory, with state/plan mode 0600 or stricter. Raw tool/API failure diagnostics are written only to unique 0600 files beneath its 0700 `diagnostics` directory; public output prints their paths, never their credential-bearing contents. Existing resources are never imported, deleted, or adopted. A failed or uncertain apply requires authoritative state/provider inspection before any new action.

The `fresh-schema` phase reads the private state's exact D1 id and delegates to the isolated published-Core executor in `scripts/deploy-integration-schema.mjs`. Its mutation boundary is a rollback-qualified D1 REST statement batch, exact Core 4.1.14 SQL and 35-file SHA map, one atomic batch from each immutable migration+ledger script, with an exact ascending ledger-prefix readback after each file, no blind retry, and read-only reconciliation after an uncertain response. `activate` checks the exact 35 published migration filenames in the isolated D1 ledger before any Worker plan. It then requires an explicit test-owner password hash, distinct 64-hex encryption key and session salt, all supplied as ephemeral environment variables, and accepts only creation of the Worker, queue consumers, and hourly cron. The root module's OIDC defaults remain empty and unpinned owner claims remain disabled. No secrets belong in the target file; OpenTofu state remains sensitive private operator material.

`fresh-schema` remains fresh-only and refuses every nonempty application schema. `recover-prefix32` is a separate, fixture-specific forward path for the isolated Commu D1 only. Before it writes, the phase validates the exact D1 identity and absent target Worker, regenerates an offline prefix-32 reference using the pinned Core 4.1.14 runner and raw SQL, and a full-35 reference using the same runner with the admitted REST statement projection for migrations 0034–0036. It then compares a new ordered 32-row ledger snapshot, every schema object, all table counts, `sqlite_sequence`, fixed FTS seed bytes, and zero foreign-key violations against the prefix-32 reference. The remote reads are sequential and cannot exclude an out-of-band writer. It validates but does not send the runner's ledger-init statement. The pinned runner must skip exactly the first 32 files and submit one existing atomic REST batch for each of 0034–0036; each ledger readback must match the exact growing 33/34/35 prefix before the next write. Final schema, seed, sequence, foreign-key, and ledger readback must match the Core-35 reference before it returns `APPLIED`. A pre-write mismatch refuses without D1 writes; any uncertainty after a batch is sent stops without retry, cleanup, or replay and requires a separate read-only reconciliation. This phase does not add a probe, general resume behavior, or a route for other databases. Its use also requires the operator's separate exact-commit/single-use evidence gate and independently qualified same-batch D1 rollback plus complete 35-migration proof; those prerequisites are not supplied by portable tests or this source phase. Meet's comparison on isolated diagnostic databases supports the parenthesized SQL form but does not establish the exact cause in Core's 0034 migration, a full 35-migration result, or Commu recovery. The Commu recovery phase remains on HOLD until the independent Meet full-35 proof and Commu's own exact prefix qualification are complete.

The `test-owner-auth` phase applies only to this already-activated isolated Commu fixture when the activation driver has discarded its test password before first login. It requires the exact 10 managed plus one data-source state addresses, the pinned Worker artifact and binding closure, the published Core 35-migration ledger, either no custom domain or exactly one identical domain record in both hostname and Worker inventories (matching id, hostname, zone, service and production environment), and zero rows in both `actors` and `sessions`. It accepts only an ephemeral canonical PBKDF2 `salt:hash` value in `TF_VAR_auth_password_hash`, then sends one secret-only Cloudflare API PUT for `AUTH_PASSWORD_HASH`. It never logs or writes the hash, request, or provider response. It requires a new sole active Worker Version at 100 percent, unchanged non-secret binding targets and secret binding names/types, and exact published module bytes before reporting readback; the later fresh-password login proves the opaque secret value. A failed or uncertain PUT/readback stops without replay or Terraform write. This out-of-band secret change makes private Terraform state stale until separately reconciled. The plaintext test password remains only in the new operator driver's memory for the later smoke. This phase does not rotate production credentials.

The `domain` phase requires the exact activated state and no pre-existing custom domain for either the hostname or target Worker across complete filtered inventories. It asks the Worker Custom Domain changeset for exactly one addition and empty `updated`, `removed`, and `conflicting` arrays (missing arrays are refused), repeats the custom-domain inventory, then writes with `override_existing_origin:false` and `override_existing_dns_record:false`. It reads back the exact hostname, service, and zone. A Worker Custom Domain adds DNS and TLS automatically; the account's current credential cannot read zone DNS, so a public DNS lookup is insufficient to prove absence of an existing record. The changeset and no-override provider flags are the mutation boundary. A failed or indeterminate write needs authoritative readback before any retry. Ordinary noninteractive Wrangler custom-domain publication is unsuitable because it can force override flags. Do not attach a route or take over a wildcard.

Set `YURUCOMMU_INTEGRATION_TARGET` to an absolute link-free 0600 JSON file under a 0700 directory outside all Git worktrees. Its exact keys are `accountId`, `zoneId`, `origin`, `prefix`, `releaseTag`, `artifactSha256` (64 lowercase hex), `sourceCommit` (clean 40-hex HEAD), and `stateDir` (an existing 0700 directory beneath the target's private parent). The exact origin, prefix, tag, and artifact digest are checked against source. The operator supplies only an existing OAuth credential as an ephemeral child-process `CLOUDFLARE_API_TOKEN`; activation additionally requires `TF_VAR_encryption_key`, `TF_VAR_session_hash_salt`, and `TF_VAR_auth_password_hash` from ephemeral process environment. Do not put credentials in command arguments, the target file, or source. OpenTofu state and plan inevitably retain sensitive values and therefore stay in the private operator directory; raw diagnostic files may also contain sensitive provider output. `APPLIED` for resources/activation means only exact create-only OpenTofu plan and private state-address readback. Before claiming a live integration peer, the operator must independently read back the authoritative Worker code artifact/digest and bindings, both Queue consumers and cron, the custom domain, and actual user/auth/storage/federation/browser behavior. The operator must review authority and irreversible effects before each mutation. Later routine code updates require a separate predecessor-preserving integration code surface; the current production `yurucommu-worker` surface remains production-only.

The portable bundle's deliberate D1-safe 0003 override is validated through the owning bundle generator; this fresh native D1 lane executes the exact published Core SQL files, and validates all immutable inputs before its first probe write.

The fresh-schema executor validates the pinned Core runner's complete script, then uses the installed Wrangler SQL splitter to preserve each compound trigger as one statement. A lexical whitespace shim handles its `(CASE` and `END)` boundary defects without changing quoted tokens, comments or the pinned SQL files. For the exact pinned 0034 `media_staged_process_input` trigger only, it also projects the standalone `SELECT CASE … END;` guard to `SELECT (CASE … END);`. This projection requires the pinned 0034 digest, the unique exact guard statement, and its trigger context; it leaves the published SQL file, hashes, and all other migration statements unchanged. A diagnostic comparison on isolated Meet databases found the bare form failed with D1's incomplete-input error while the parenthesized form reached the deliberately late constraint failure with schema readback unchanged. That supports the transport shape only; it does not establish Core's exact 0034 failure cause, complete all 35 migrations, or qualify Commu recovery. The executor sends exactly one REST `{batch:[{sql}, …]}` request per migration, with ledger initialization first and the matching migration mark last. It requires the exact result count and successful, error-free results for every statement. Before any real migration, the same batch transport creates probe tables, a nested-CASE trigger and a synthetic ledger mark, then deliberately fails a late duplicate-key insert. Readback must find no probe tables, trigger or ledger; a parser failure, residue or uncertain response stops without cleanup or retry. Portable SQLite tests prove request shape and refusal behavior; real D1 trigger parsing, batch rollback and all 35 migrations still require isolated live qualification. A database with earlier migrations remains non-fresh even when user tables are empty; this phase provides no resume path.

Activation rechecks the complete Worker inventory before planning and immediately before apply. The Cloudflare Worker upload is a PUT, so these reads cannot atomically exclude a concurrent creator with the exact same reserved fixture name; a create-only private plan is not remote conditional-create proof. A collision is refused and any uncertain upload is reconciled without replay.

A newly created remote D1 contains the reserved `_cf_KV` table. The empty-schema guard ignores only exact `_cf_KV` and `_cf_METADATA` objects whose type is `table`, alongside SQLite system objects. Application tables, `_cf_` lookalike names, views and triggers still stop the run before the rollback probe or any migration. This matches the reserved-table behavior in [Cloudflare D1 import/export documentation](https://developers.cloudflare.com/d1/best-practices/import-export-data/); it never reads or deletes reserved-table contents.
